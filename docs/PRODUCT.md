# ytrader 产品需求（PRD）

2026-10-15 重建基线。状态：产品基线；首个真实闭环正在实现，完整P0尚未验收，未部署。当前进度以CHECKPOINT为准。本文由产品经理起草、CEO审阅整合，是待工程验证的产品基线；默认值是设计决策，不是已验证事实。团队见 TEAM.md，技术实现见 ARCHITECTURE.md，交付门槛见 DELIVERY.md。

## 1. 产品承诺与非目标

**一句话**：每天打开，不用做任何选择，就能看到这一天值得关注的变化：它为什么重要、可信到什么程度、相比上次有什么新变化，以及它通过什么机制影响哪些产业环节和 A 股公司；证据不够时，产品明确停下来。

**首版承诺（P0）**
1. 首页“今日大事”自动筛选，不要求用户先选产业、公司或方法。
2. 事件页：事实 → 机制 → 环节差异 → 公司落点 → 证据与不确定性。
3. 事件生命周期：可以更新、更正、辟谣、出现冲突、过期，用户都能看到。
4. 独立个股分析（辅助入口）。
5. 来源与更新状态如实显示：“没有新内容”和“抓取失败”分开。
6. 单人访问控制；桌面 Web 和 iOS 应用。

**明确非目标**：买卖建议、目标价、涨跌预测；持仓、交易、回测；推送通知；多人账户；复杂多跳图谱和可视化大屏；全球全量新闻覆盖；Android。产品不输出任何“建议买入或卖出”的措辞。

## 2. 入选、证据与新变化

三个维度分别判断，输出类别和可核对理由，不展示未校准的概率分数。

**重要性**：重大 / 关注 / 不入选。重大须说明影响规模、持续性或紧迫性及其具体依据：如主要供需成本、政策约束、或单一公司的主营/存续/控制权发生重大变化。环节数量、报道热度、已知股票数都不能单独决定档位。一般但有实质经济/产业/公司影响的变化为关注；无新变化的转载、纯情绪争论不占首页。重要但产业影响尚未覆盖的事件照常保留事实，写清缺少什么，不因此丢掉事件。

**证据状态按断言记录**：原始依据支持 / 独立报道支持 / 未核实 / 冲突 / 已被否定。事实、来源观点、条件推断则是独立的内容类型。当事人原话只证明“某人说过”，不能自动证明话中全部断言；同源转载不算独立证据。事件卡的状态对应它的核心断言，不能用一个总分掩盖内部冲突。

**新变化**：新事件 / 实质更新 / 无实质变化。事实、数字、证据状态、事件状态或影响判断改变才是实质更新；增加转载和措辞优化不自动让用户重读。对照前一已发布版本判断变化，而不是用取得时间伪装发生时间。

**事件同一性**：同一原始事项的转载、补充报道、回应和辟谣沿用事件；仅仅同公司、同日期或同主题不能合并。主体、动作、对象、地点及发生/生效时间能相容，且能关联到同一原始事项时才合并；跨天报道不因此另建事件。独立的新行动或再次发生的事故建立新事件并关联旧事件。无法判定时保留独立记录和待核对关系，不能强合并事实。合并/拆分必须可追溯。

每个已发布事件版本明确选定一个**核心断言**，标题、卡片证据标签及主列表/观察区路由都由这个断言决定；其他断言分别保留状态。不得把“官方宣布调查”和“未经证实的违法传闻”混成一条已确认事实。

**入选与排序（默认决策）**：
- 主列表收重大/关注且核心断言有原始依据或独立报道支持的事件；冲突事件若至少一方有原始依据，列明冲突后可入选，不能无条件采用一方结论。
- 重大且未核实，或冲突双方均无原始依据，进入“观察中”；最多3条，只解释若成立的影响。已被否定的断言不作为有效新事件入选，但相关更正进入更新提示。
- 排序依次为重要性、是否实质新变化、最近实质变化时间，最终以稳定事件ID排序避免闪动。主列表最多10条，无下限；溢出从“更多”查看。
- 首页“今日大事”采用滚动24小时的新事件/实质更新，时间按北京时间显示并标明。历史可回看；离开首页不等于事实失效。

## 3. 用户路径与信息层级

**首页（从上到下）**
1. 状态条：最近成功更新时间；来源状态（正常｜部分来源延迟｜更新失败，并附失败时间）。
2. 今日大事。卡片字段：一句事实、一句影响、重要性档位及入选理由、核心断言的证据状态、新变化标签、发生时间、最近核验时间。
3. 观察中（待证实）。
4. “有更新”：以前看过、现在出现实质更新的事件。
5. 公司搜索入口。

空状态是两种不同文案：“本次更新未发现新增重要事件（最近成功更新 HH:MM）”和“更新失败，以下为 HH:MM 的内容”，不能混用。

**事件页动作与返回**
- 证据：每条事实可以展开来源（标题、发布方、发布时间、原文链接）；打开原文后返回，停在原来的滚动位置。
- 公司：点公司进入公司页，页面带上本事件的上下文（该公司在环节中做什么、关联依据）；返回回到事件页原位置。
- 环节：同一事件按环节分别给方向（偏正面｜偏负面｜不确定），不给整个事件一个总标签。
- 用户操作：查看证据、进入公司、切换独立分析方法并显式刷新。首版不增加“不关注”和投诉工单。打开事件当前版本成功后记录已读；读取失败不得标已读。
- 证据断在哪里就停在哪里，显示“到此为止：缺少 X 证据”，不硬造环节或公司。

**内容区分**：事实、来源观点、条件性分析三种内容用不同的视觉样式呈现，条件性分析必须写出成立条件和反向因素。

## 4. 生命周期、更正与过期

| 维度 | 取值/规则 |
| --- | --- |
| 事件状态 | 进行中 / 已结束 / 不成立；改变必须有证据，不能用几天无更新推定结束 |
| 证据状态 | 按断言记录，引用不可变来源版本；每次变更保留理由和来源 |
| 分析状态 | 当前 / 需重算 / 已撤回 / 生成失败；结论记录依赖的断言及版本 |
| 读者状态 | 已读事件版本；新实质版本高于已读版本时显示“有更新” |

首页窗口和有效性分开：未核实消息7天无新证据可退出观察区，仍为未核实，不能自动写成假消息。历史可搜索。更正卡片醒目展示72小时；事件页保留更正标记及许可允许的变更记录，用户未读的重要更正仍可在“有更新”回查。

- **实质更新**：列“自你上次阅读以来的变化”，旧已读记录不覆盖新版。
- **冲突**：并列来源与分歧，相关影响保留条件，不抹平为统一事实。
- **更正/否定**：立即撤回依赖错误断言的推断和公司落点；有独立依据的业务关系保留。重算尚未完成或失败，错误旧结论也不能继续作为可用内容展示。
- **普通刷新失败**：依赖仍有效的上次结果可标旧保留；无任何成功结果则明确未生成，不展示半成品。
- **过期**：来源采集时效、分析刷新时效与事件是否结束是三件事。必须分别显示。

补证、重算、降级按规则自动执行，不把日常使用建立在人工审批队列上；无法自动解决时停在明确的未知状态。使用条件要求删除原文时删除相应内容，只保留允许保存的来源标识、更正和不可用说明。

## 5. 公司与独立分析

输入公司名或代码即可进入公司页；公司身份用证券市场+代码确定，同名不能混用。先展示主营、所在环节、业务依据及资料日期；从事件进入时保留事件上下文。概念标签不是供应合同或盈利影响证据。

产业成员名单只产生候选。事件页展示某家公司，必须同时有事件机制依据、该公司的相关业务/成本/地区等暴露依据，以及连接两者的事件级条件推断。新闻不必直接点名公司，但不能只因“它属于这个行业”就当作确定受益或受损；无法建立这条证据连接就停在环节。公司经营背景与本次事件影响分开展示。

经营基本面和事件影响为独立页签；首次默认经营基本面，用户明确切换，不因是否有新事件自动跳方法。每种输出为简明结论、3–5条理由、风险与反证、数据截止时间及来源。必需数据缺失时列缺项，仅展示已知事实，不补造结论。

- 读取已保存结果不触发模型。超过24小时提示可能过时；这是默认刷新策略，不是事实的有效期。后台按已配置计划和相关证据变化触发更新。
- 用户显式刷新走异步任务。默认每公司每方法每小时最多1次、单用户每天10次；重复点击归并到同一任务。此为待测技术额度，不是付费授权。
- 自动与手动分析共用服务端模型预算；未配置产品凭据或费用硬上限时禁止付费调用。预算耗尽暂停新分析，已有有效结果照常可读并说明状态。
- 刷新失败显示原因类别、失败时间及上次成功结果；依赖被更正或否定的旧结果按第4节撤回。没有成功历史显示“暂不可用”，不能返回空白当作无风险。
- 返回事件/列表保持来源位置；登录失效要求重新登录，不能因此丢失已保存分析。

## 6. 需求与验收

| ID | 需求 | 可判定结果 |
| --- | --- | --- |
| R1 | 零选择阅读 | 首页直接呈现合格内容或明确空状态，无需先设行业/股票 |
| R2 | 入选与排序 | 产品经理先给边界样本及预期，逐条检查档位、理由、观察/主列表和新变化；不以模糊通过率代替规则 |
| R3 | 不凑数 | 无合格新增时不填低质事件，来源成功时间明确 |
| R4 | 来源与结果状态 | 失败、部分失败、未配置、过期与无新增可区分，不把旧数据标最新 |
| R5 | 内容和证据 | 事实可追溯、观点有归属、推断有条件和反向因素；缺时间标未知 |
| R6 | 产业与公司证据 | 重要而未覆盖的事件保留；关系不足停步，不编造公司关联 |
| R7 | 更新与更正 | 断言变更使依赖失效；否定只撤回相关推断；历史可回查；重算失败不恢复错误结论 |
| R8 | 已读版本 | 实质更新提示未读，无实质变化不重置；旧设备回写不得降低已读版本 |
| R9 | 个股分析 | 方法独立，缓存读取零模型调用；重复刷新去重，额度/失败/缺数据正确呈现 |
| R10 | 连续阅读 | Web/iOS 的事件、公司、原文之间往返保持上下文和滚动位置 |
| R11 | iOS 交付 | 签名应用在iPhone上完成登录和主路径；弱网/离线有时间与状态，不截断或横向溢出；模拟器不替代真机 |
| R12 | 运行可靠性 | 实际更新、来源/模型故障恢复及服务重启后持久状态正确；更详细的发布门见 DELIVERY.md |

首次用少量代表资料：重大非财经变化、政策/原始披露、公司事件、传闻与辟谣、来源冲突/更正、旧闻/无新增，以及独立分析缺数据。边界用例可组合在少量样本内；真实资料和预期在生成前冻结。历史更正可按原始顺序回放，明确标记回放；故障由可丢弃环境注入，不制造虚假新闻。真实样本尚未收集，不把类型清单当验收证据。

关键错误出现即不通过：编造来源/数字/时间/公司关系；把未核实或被否定断言当事实；错误分析未撤回；无新增与失败混淆；出现买卖、目标价或确定涨跌结论。非关键偏差写明修改规则或实现的理由，不能事后改预期掩盖缺陷。

稳定性不能由文档、一次模型输出或一次运行证明；首次交付验证具体故障和恢复路径，之后按运行记录观察，不用无依据的固定等待天数代替判断。

## 7. 质量底线

能查到数据、页面能点击、模型能返回文字，都不等于完成。模型生成的通顺解释，如果没有可追溯的证据，按缺陷处理。

## 8. 示意（假设机制，非事实）

假设某地区局势紧张，可能带来运输风险，进而可能影响油价预期。传导到不同环节方向不同：上游可能受到支撑；炼化取决于价差；航空、航运承担成本压力。每一步附成立条件（库存、合同、对冲）和反向因素，最后才落到有业务依据的公司。此段只说明结构，不断言任何事件。

## 9. 外部依赖与责任

| 依赖 | 阻塞点 | 责任与解除条件 |
| --- | --- | --- |
| 持续发现来源及使用条件 | 真实事件链路、覆盖验收 | CEO组织核验，架构师确认接入；至少有已验证广泛发现和原始补证通路，标明覆盖边界 |
| 产品模型provider/凭据/费用授权 | 自动解释和独立分析联调 | CEO核实已有可用服务与预算，架构师验证硬上限；开发agent OAuth不等于产品服务授权 |
| 财务与公司资料权限/字段 | 经营基本面方法 | CEO核实iFinD权益及披露替代；架构师明确缺字段处理，用户仅在账号资料不可获取时配合 |
| iOS签名/设备 | 真机交付 | 架构师先核对现有环境，确需账号或设备时再请用户提供；不能提前声称已可安装 |
| 主机/恢复/监控 | 稳定运行验收 | 架构师提供方案并在允许环境验证；资源不足由CEO调整，不擅自采购 |

用户只决定目标、重大取舍、外部权限和必要付费，不承担常规调研。缺少首版纠错入口的残余风险由CEO记录；用户初期可通过Codex反馈，后续是否加入入口按真实使用决定。

## 10. 本轮产品经理与CEO的决策

采纳：分类加理由、主列表10条无下限/观察区3条、证据与内容类型分离、四维状态、读缓存不调用模型、明确用户操作与状态。

修正：不用产业覆盖程度排除重要事件，不按静默时长判事实失效；更正依赖必须立即撤回；首版不加投诉/屏蔽系统；默认经营基本面；滚动24小时窗口避免零点丢失阅读价值。

采纳产品经理反对意见中的历史资料回放建议；保留删除纠错入口的残余风险。后续变更由产品经理说明行为和验收影响，再与架构师对齐，不逐句追加功能。
