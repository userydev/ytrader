# ytrader 开发计划（V0 · 双仓模块化交付）

> 2026-10-15。新项目从零开发，`docs/PRODUCT.md` 是唯一产品定义。Y-Core 和 ytrader 是**两个独立仓库与运行服务**，不是两个分别决定金融产品方向的团队。不继承旧工程、回测或交易计划。

## 1. 当前架构决定

- **Y-Core = Radar + AI 两类基础服务**。Radar 获取新闻和保留出处/版本；AI 提供可复用的受控任务执行及必要的预算/故障恢复。这两类能力所需的调度、存储与运维属于实现细节。
- **ytrader = 新闻阅读 + 产业目录 + 新闻关联 + 板块与公司 + 个股策略 + 可选传导分析**。行业归属、业务映射、策略和可见交互全由 ytrader 定义。
- **首个可用交付只做真实新闻展示与产业链关联**。传导分析、板块公司深度资料、个股多策略属于后续独立模块，不准绑成一次巨大开发。
- 新闻/产业/公司页面的基础读取不得隐式执行收费分析。用户可以决定是否深入分析；自动关联能力分阶段验证，不预建通用工作流配置平台。

## 2. 模块所有权 / 依赖规则

| 位置 | 模块 | 自己负责到哪里 | 明确不负责 |
| --- | --- | --- | --- |
| **Y-Core** | Radar | 数据源适配、拉取/去重/修订、时间和出处、读取接口、源健康 | ytrader 的产业链/板块/股票语义和「受益」判断 |
| **Y-Core** | AI | 模型执行、结构化返回、任务标识、费用上限、状态和恢复 | 固定股票分析策略、ytrader 业务 prompt、研究结果库 |
| **ytrader** | News | NewsCard/详情/来源、时间、筛选和阅读；消费 Radar | 重新采集新闻或私建另一套公共去重 |
| **ytrader** | Industry | 产业链及环节的结构化目录和阅读交互 | 认为一条新闻必然影响链上所有公司 |
| **ytrader** | Association | 新闻与产业链的候选/已确认关联、来源/依据、纠错 | 把关联算法变成 Y-Core Radar 的固定能力 |
| **ytrader** | Sector/Stock | 产业环节的板块与公司业务关系、基本资料 | 将业务关联自动转成利好买卖指令 |
| **ytrader** | Strategy | 独立策略定义、输入验证、结果解释、引用和保存 | 在 Y-Core 中硬编码策略 |
| **ytrader** | Impact | 按用户选择的新闻和环节分析可能的传导路径 | 自动作为所有新闻的强制处理步骤 |

**共享数据的单一写入权**：Y-Core 写公共 Radar 原件及其版本；ytrader 记录自己的 news↔chain 关联、产业结构/板块/公司映射和分析结果，只引用对应原件 ID/版本。财务和证券行情如在阶段中确有需要，首期由 ytrader 的独立数据适配模块负责；以后有跨产品复用需求再评审是否迁为共享供给。

## 3. 分阶段交付

| 阶段 | 目标与 ytrader 结果 | 对 Y-Core 的需求 | 能关闭阶段的证据 |
| --- | --- | --- | --- |
| **P0：合同与入口** | 定义 Radar 消费适配层与新闻/产业链最小数据模型；用带日期的真实静态样本验证新闻卡片和链标签体验 | 审定最小 Radar 读取语义；不要求搭建全套 Radar 平台 | 同一份契约样本可在 ytrader 页面显示，正例/反例区分，职责表无重复实现 |
| **P1：首个可用版本** | **真实新闻列表 + 来源详情 + 相关产业链标签/入口**；产业链至少可打开基础介绍 | 一个可靠且使用许可明确的真实新闻源、可读 API、版本/时间/覆盖、错误/变更状态 | 使用真实 Y-Core 返回，2 条相关新闻能定位产业链、1 条不相关不会强行关联；源失败仍能正确提示 |
| **P2：产业链阅读** | 链的环节结构、板块与公司基础关联，点击可展开来源和理由 | 无新增必需服务，除非实际数据缺口证明需要 | 新闻可进入正确链/环节，再看到板块、两家有业务资料支持的公司；不把「业务存在」说成「受益已证实」 |
| **P3：个股多策略** | 直接搜索个股、公司资料、两个方法不同的策略视图及证据 | Y-Core 通用 AI 执行合同；若确需行情/财务，ytrader 通过明确适配器取得 | 同股两策略展示不同输入、方法、结论/反证和缺口；AI 失败不阻断公司资料页 |
| **P4：可选传导分析** | 从新闻或产业链点击「分析影响路径」，展示条件链、反证和局限；非自动必经 | 使用现有通用 AI 任务，不新增 Y-Core 股票专用 AI API | 用户主动触发、运行状态清楚、旧结果可读；与产业结构/公司业务映射不混淆 |
| **P5：选择与自动化** | 基于真实使用反馈，加入产业筛选、需要的自动关联或更新开关 | 现有能力足够先复用，缺口明确后再扩展 | 用户可选择分析频度和功能，不配置也能正常浏览基础内容 |

**P1 是第一个应尽快实际可用的版本**。P2–P5 不应该成为 P1 发布的前置条件。分析策略可以在个股资料完整时独立交付，不必依赖传导模块先完成。

## 4. 最小跨仓消费合同（先定义行为，后确定 URL）

### Radar → ytrader（只读）

Y-Core 至少返回这些稳定信息：`document_id`、`revision`、`title`、`publisher/source`、`original_url`、`published_at`、`observed_at`、可用 `summary/body` 和 `coverage`（仅标题/摘要/可读材料）以及错误/源状态。允许按时间获取最近资料并打开详情；同一材料更新可观察，不因摘要或 AI 未就绪导致基础阅读被阻断。字段名称以双方最终实现合同为准；不把这里的概念名冒充已发布 API。

### AI → ytrader（有权限的任务执行）

ytrader 送入 `task_key`、`input`、`expected_schema`、模型能力/资源上限及业务任务关联；Y-Core 返回 `run_id`、明确的 `status`、结果/错误和费用状态，并支持使用同一 key/ID 找回结果。Y-Core 可以不理解输入中的 `industry_id` 或 `strategy_id`，这些是 ytrader 私有业务语义。

### ytrader 内部领域合同

- News：`document_id + revision`，用户读到源材料。
- Chain：`chain_id` 与 `node_id`，存在于新闻之外。
- Association：`document_ref → chain_id`，包含理由、证据、来源方式（人工/规则/AI）和状态（候选/已确认/拒绝）。同一新闻可关联多条链或 0 条。
- Sector/Stock：`node_id → sector_id / security_id`；必须有业务依据且不赋予事件影响结论。
- Impact/Strategy：有明确版本、资料引用、业务输入/输出、状态和错误；**仅在用户明确调用或启用相关自动选项时执行**。

技术负责人可在实现阶段决定具体框架、数据库与结构，但不可将这些语义混为一张万能 `relevance` 或 `stock_score` 表。

## 5. Codex 双仓开发工作制

1. **需求起点在 ytrader**。每个阶段由一个用户能实际操作的页面场景驱动，只确定本阶段必要的 Y-Core 输入/任务合同。
2. **同一契约样本**。先从 ytrader 写出预期展示与正/反例，Y-Core 按合同提供真实数据；ytrader 使用可替换的 Y-Core adapter，开发前期可用清楚标注的契约样本，正式验收必须是真实 Y-Core。
3. **分开实现、联合验收**。各仓库自己维护代码、测试和 PR；一次合同变更同时核对消费者，不能靠文档想象兼容。Y-Core 提供能力成功 ≠ ytrader 产品可用。
4. **一个阶段、一个主目标**。Codex 可独立调度子代理阅读、测试和调研，但不得额外扩建数据平台、通用 Agent 管理台或复杂设计系统。不以局部测试通过关闭用户路径。
5. **输出保持精简**。每轮只报告：可打开的用户入口、已跑通的路径、真实来源/数据缺口、失败状态及下一步。不新增无必要的长期计划副本。

## 6. 本轮决定和暂缓

当前只批准**产品边界和计划草案**，不视为授权正式开发、生产部署、付费模型调用或仓库合并。此文档更新在 Draft PR 中，准备供用户评审。

暂缓但不永远排除：自动化策略、个人自定义规则编辑、全市场产业关联、连续深度研究、复杂图谱、回测、交易/持仓及付费订阅。只有当前用户场景暴露具体缺口，才单独加到活动阶段。
