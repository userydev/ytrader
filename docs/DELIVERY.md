# 交付门槛与运行验收

本文件把产品需求、系统设计和真实验收连接起来。所有运行项当前均为**未执行**，文档检查不改变此状态。不靠固定等待天数、样本数量或模型自报PASS判断稳定。

## 1. 三个放行点

| 放行点 | 必须具备 | 当前状态 |
| --- | --- | --- |
| 研发基线 | 产品行为/状态、系统对象/API、故障与预算规则一致；角色分工明确；工作包有依赖和验收；用户明确同意开发 | 文档已补齐并经CEO整合；用户尚未授权应用开发 |
| 真实产品链路 | 可持续取得的发现来源与原始补证、产品模型服务与预算、足够的公司资料；真实冻结样本跑通完整解释和停止推演 | 尚未完成完整联调；已有RSS、iFinD及一次真实模型探针，范围和剩余条件见READINESS |
| 稳定可用交付 | 内容边界、双端实际使用、故障恢复、持久化、费用控制、身份隔离、备份恢复与发布回退有证据，用户接受体验 | 未执行；不能因文档/接口/模拟器通过提前宣布完成 |

真实依赖核实由CEO组织，架构师判断约束；用户只补无法取得的账号、设备或必要授权。无需用户逐项选择技术或代做调研。

## 2. 需求到验收的对应

| 关联 | 必须检查的行为 | 最小证据 | 判断责任 |
| --- | --- | --- | --- |
| R1–R3 | 无选择阅读、入选/观察/排序、不凑数；同事件转载归并、不同事项不误并 | 冻结资料+预期，实际首页和归并记录 | 产品经理定预期，Codex核对 |
| R4 | 全/部分来源失败、无新增、过期、未配置互不混淆 | 一次实际成功更新及可丢弃环境故障记录 | 架构师定状态，Codex验证 |
| R5–R6 | 核心断言控制路由，观点与事实分开；每个公司落点有事件级业务证据连接 | 原文/版本/支持位置与输出对照，含缺证停止样本 | 产品经理+Codex；Grok按新盲点质疑 |
| R7–R8 | 更正只撤回依赖结论、旧快照不继续显示有效；跨设备已读不回退，合并不乱迁版本 | 真实历史更正回放+API/界面状态记录 | 架构师+Codex |
| R9 | 独立方法、只读零调用、重复刷新不重复派发、额度与失败正确处理 | 服务端任务/模型派发记录，不能只看按钮文案 | 架构师+Codex |
| R10–R11 | Web及iPhone登录、阅读、返回、外链、弱网/离线与过期退出 | 浏览器实际路径及已签名真机记录；模拟器单独标记 | Codex，用户最终体验接受 |
| R12 / T1 | worker重启、租约竞争、超时未知不会造成重复发布或盲目计费 | 可丢弃数据上的重启/故障记录与幂等键对照 | 架构师+Codex |
| T2 | 日/月预算原子预留、未知占用跨期保留、未授权provider不调用 | 并发边界/结算与拒绝记录，零预算时无外部请求 | 架构师+Codex |
| T3 | 登录、会话失效与撤销、CSRF、产品服务凭据隔离 | 对应接口检查及双端退出验证；密钥不进客户端产物 | 架构师+Codex |
| T4 | 游标过期后固定水位快照恢复，不跳过恢复期间更正 | 水位、引用状态和回放结果；不可恢复缺口显式存在 | 架构师+Codex |
| T5 | 备份可恢复、迁移可回退、恢复后阅读/依赖/任务一致 | 在隔离环境恢复一次，核对版本和实际路径；不只比较行数 | 架构师+Codex |
| T6 | 约4GB环境内运行无持续积压/OOM，staging不损害生产 | 实际峰值资源、积压年龄和任务耗时；不足则停staging/调方案 | CEO裁决资源，Codex实测 |

这是一组验收目标，不要求为每个表格行编造独立测试套件。一次有意义的故障场景可以覆盖多个目标。代码变动只跑受影响检查；通过后没有新问题不反复自审。

## 3. 样本与内容质量

产品经理先冻结每类代表资料的来源、取得时间、原始版本与预期行为，覆盖：重要非财经变化、政策/公司原始披露、传闻和否定、相互冲突、旧闻重复、产业未覆盖/公司缺证，以及分析缺字段。用同一小组样本覆盖多个边界；自然更正可按历史顺序回放，明确不是实时运行证据。

编造来源/数字/时间/公司关系、核心未核实断言被当事实、否定后仍显示有效结论、模型重复派发导致不受控计费，均阻止相应能力放行。不能事后修改样本预期来掩盖实现错误；规则调整必须说明理由并同步产品/架构正文。

## 4. 运行、故障与恢复责任

- ycore记录来源成功水位、鉴权/限额失败、模型派发/预算/unknown；ytrader记录事件/证据版本、业务任务、撤回与积压。日志不含token、密码或全文资料。
- 临时故障按有界策略自动恢复；永久鉴权、模型结果未知、备份失败和持续积压交运行负责人Codex处理。每条事件不需要人工批准，异常处理必须有可见入口和负责人。
- 发布前落实监控入口和经用户允许的异常通知方式；当前没有创建提醒或自动消息。仅写日志而无人能看到异常，不满足长期运行门槛。
- 设计目标：每日机外加密备份，RPO24小时、RTO2小时；这是待演练目标，不是当前承诺。恢复失败不能以“备份文件存在”通过验收。
- 若模型服务停用，保留仍有效的旧内容，显示解释未生成/预算或权限原因；不能把纯事实摘要版本作为完整解释产品交付。

## 5. 当前缺口与推进顺序

1. CEO核实已有来源、模型服务权限、预算和可用资料；架构师将结果落实为具体配置与限制。没有此证据，不能批准真实自动分析的上线。
2. 用户同意开发后，工程师按固定PRD/契约实现最小真实流程，优先验证取源、事件/断言/公司证据连接以及iOS认证/签名条件。
3. 内容与状态成立后再扩展公司分析和双端阅读；随后运行对应故障、恢复和资源检查。
4. Codex提供可审阅的运行结果，用户接受实际体验；缺少真机、备份或核心来源仍算未完成，不以更名“首版”跳过。

文档完善使开发可执行，真实运行证据才支撑稳定交付。当前不签发“已具备稳定产品交付能力”的结论。
